# Project Architecture — Global Tech Docs

This file explains the high-level structure of the repository and how the pieces fit together so new contributors can quickly understand "what they're looking at".

Key components
- `dita-ot/` — Embedded DITA Open Toolkit used to build HTML and PDF outputs. Contains plugins, scripts, and configurations.
- `topics/` — Source content organized by topic type and purpose:
  - `topics/guides/` — Practical, production-focused guides (recommended primary path).
  - `topics/examples/self_referential/` — Learning artifacts that explain how topics work (keep these as teaching examples).
  - `topics/examples/generated_openapi/` — Auto-generated API topics (created by the generator script under `tools/`).
  - `topics/references/` — Reference topics (API, CLI, formats).
  - `topics/tasks/` and `topics/concepts/` — (If present) other topic types.
- `maps/` — DITA maps which assemble topics into deliverables. The primary map is `maps/service_manual.ditamap`. We also generate `maps/generated_api.ditamap` when running the generator.
- `out/` — Build outputs (HTML, PDF). These are generated artifacts and not the source of truth.
- `.github/workflows/` — CI workflows: validation & builds, accessibility checks, and GitHub Pages publish.
- `tools/` — Utilities (OpenAPI→DITA generator and its package.json).

Data flows and developer workflows
- Author content in `topics/`. Prefer small, focused topics (one task, one concept, one reference).
- Update `maps/service_manual.ditamap` to include new topics (or use the provided structure). The map controls what gets built.
- Run local validation & build using the DITA-OT binary in `dita-ot/bin/dita` (see the Developer Guide for commands).
- CI (GitHub Actions) will:
  1. Validate DITA map and topics
  2. Build HTML output (`out/html5`) and PDF (`out/pdf`)
  3. Run accessibility checks (pa11y) and upload reports as artifacts
  4. Publish HTML to GitHub Pages from `out/html5` (on push)

Why structural decisions
- Keep learning artifacts under `topics/examples/` so they don't mix with production guides.
- Generated API topics live under `topics/examples/generated_openapi/` to make it explicit they are generated and can be re-generated by the `tools/generate-dita-from-openapi.js` script.
- Use `conref` for shared warnings/notes and `keyref` for standards/terms to minimize duplication and centralize updates.

Where to look first
1. `docs/DEVELOPER_GUIDE.md` — step-by-step commands for local work.
2. `topics/guides/technical_writer_guide.dita` — guidance for writers collaborating with engineers.
3. `maps/service_manual.ditamap` — canonical build map; shows what is included in outputs.
